## Map-tool reliability pass before the final release

The server already has `hoi4.map_inspect`, `hoi4.map_render`, and `hoi4.map_rewrite` for province, state, region, adjacency, supply, rail, position, and source-linked changes. Its navigator, tiles, exact coordinate lookup, declared operations, and atomic recovery are the agent-facing product surface. The map editor's [project workflow](https://github.com/AdriianCOE/HOI4-Map-Editor/tree/8531064bde12bd84425e714804916f36bf1ff669) supplies concrete cases to audit, not a reason to build another desktop editor.

1. Verify every advertised map operation against the installed map and synthetic fixtures: province create/update/merge/remove/renumber; state create/update/move/split/merge; strategic-region membership and renumbering; normal and special adjacency; supply nodes and railways; coastal ports, victory points, buildings, unit/weather positions, and scripted scalar references. Check inspect and render before and after each supported rewrite, including exact affected-area tiles and source hashes.
2. Review dated state history at the active earliest bookmark. Owner, controller, cores, claims, victory points, and building edits must preserve unrelated dated blocks and refuse unsafe interpretations. The map editor's candidate-first save and reload approach is a useful precedent: map rewrites must prepare all affected bytes, validate the combined candidate, apply through the existing transaction engine, recover from an interrupted later-file failure, and re-read the resulting map before claiming success.
3. Compare map constraints rather than copying them. The editor preserves sparse province IDs and reports compatibility diagnostics, while the offline HOI4 map-modding reference says gaps can shift province properties to later IDs. Keep the MCP's gap error for load-sensitive rewrites until engine evidence proves a safer rule; test that read-only inspection can still report the exact gap and remaining valid records. Apply the same evidence standard to unusual bitmap dimensions, incomplete region coverage, coastal flags, and missing definition colors.
4. Add focused negative cases for overlapping or disconnected pixels, duplicate RGB/IDs, missing state or region membership, dated-history ambiguity, invalid naval bases and crossings, stale source revisions, read-only dependency references, multi-file write failure, and reload mismatch. Run the full map acceptance and MCP integration suites on Windows and Linux, then a bounded read-only inspect/render of a real installed mod. Do not call the map tools fully working from synthetic tests alone.
5. Improve the current map tools where this audit reveals a reproducible defect, with source-linked diagnostics and a regression test. Retain bounded, declarative map requests and visual evidence; do not import brush, lasso, undo stack, or a standalone editor UI into the MCP service.

## Reference service inside the existing server

The service reads configured, authorized local roots. The public package ships code and schemas, not copied Paradox Wiki pages, installed-game documentation, third-party mod source, or game artwork. A workspace may register a wiki snapshot path; the installed game documentation path is discovered under its configured game root. Optional generated game documentation is registered by the user as another local root. Each root has a content hash, game version where known, source kind, and a clear authority rank: installed game documentation first, installed game examples second for observed structure, offline wiki guidance next, then project rules and accepted skills. Conflicting sources remain visible instead of being silently merged.

Expose a small set of tools and resources rather than a second server:

- `hoi4.reference_search`: search titles, aliases, headings, exact script tokens, and short body passages across selected source kinds. Return a bounded list of section IDs, one or two matching excerpts, file path and line span, revision, authority label, and a concise reason for the match. Default to a small result limit and fixed response-byte ceiling.
- `hoi4.reference_read`: read one returned documentation section with a bounded line and column window. Return source text without rewriting syntax, with revision-bound continuation. An unknown section, stale revision, invalid position, or unauthorized root must fail explicitly.
- `hoi4.reference_context`: select documentation for a named work surface. When a question is supplied, put its best matching sections first. Return a compact citation bundle; the caller reads the sections needed for the task.
- `hoi4.source_lookup`: retrieve exact indexed definitions, load-order and override evidence, bounded source blocks, and indexed usages. Use it for source precedents after consulting the relevant documentation.

Keep domain-specific inspect, render, compare, scenario, and rewrite tools as the evidence route for their systems. Reference tools answer syntax and precedent questions; they do not replace domain validation or the user's live-game checks.

### Index and response contract

Parse Markdown headings, anchors, fenced code, and line offsets once into immutable, content-addressed segments. Add exact-token and heading indexes before considering embeddings. Reuse core workspace identity and source-revision fencing; refresh only changed files. A search result should normally fit within roughly 2–4 KiB, and a section read should have an explicit character or line cap, stable pagination, and a link to the original local section. Measure these limits against actual task traces rather than asserting a token-saving percentage in advance.

For vanilla and mod script, expose exact symbol names, source location, owner block, shadowing status, and narrow nested-block reads through `SymbolIndex`. Do not parse a second copy of the source tree or send entire files merely because a symbol matched. For optional generated `script_docs`, retain raw entries exactly, layer parsed scopes and parameter fields only where unambiguous, and report ingestion coverage and missing documentation.

### Workflow rule change after validation

Once these tools pass the acceptance cases below, update Chaos Redux `AGENTS.md` and the relevant skills so “consult the required pages” means query the local index, read the pertinent cited sections, and keep their source links in the task evidence. The core pages remain available as required references; routine tasks need not paste all eleven full pages into the model context. Installed vanilla documentation remains primary where it covers the system. No rule is weakened before the tool can prove the right sections were consulted.

4. Benchmark at least GUI, focus, event, technology, and decision tasks against the present full-page workflow. 5. Then revise the Chaos Redux reading instructions and skill examples, document the new tools, run the full repository checks and MCP Inspector, and publish through the normal release workflow. Include a migration example that starts with a task question, returns a small context bundle, and opens one cited section only when needed.

## Ideas to defer

Do not run the other MCP servers alongside this one or copy their GPL/AGPL or unlicensed source into the Apache-2.0 package. Do not add automatic game launch, game log collection, unconstrained fuzzy edits, raw wiki-page dumps, or an unreviewed self-learning rules database. Multi-game support, embeddings, and broad AI-generated documentation can wait until the HOI4 local reference service is measured and reliable.
